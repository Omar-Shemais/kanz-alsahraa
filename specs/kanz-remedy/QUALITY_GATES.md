# تشغيل بوابات التحقق ومتابعة نتائجها

## أمر الفحص المحلي

من جذر المشروع، بعد التأكد من Flutter 3.38.4 وDart 3.10.3 وتوفر الحزم:

```powershell
flutter pub get --enforce-lockfile
dart tools/quality_gate.dart
```

البوابة تفحص تنسيق ملفات المعالجة والاختبارات/الأدوات المحددة في remediationFormatPaths دون تعديلها، ثم تحلل المشروع كله بالإعدادات الحالية، ثم تشغل جميع اختبارات test. فشل أحد الفحوص لا يمنع الفحوص المستقلة التالية، لكن النتيجة الإجمالية تبقى فاشلة. الفحص ليس دورة شراء أو اعتماد QA أجهزة أو إثبات جاهزية النشر.

التحليل الكامل لا يقتصر على الملفات المعدلة. في 17 سبتمبر كشف الفحص الأول 536 ملاحظة قديمة، من التحذيرات والملاحظات دون diagnostics من نوع error. تشمل إعدادات lints أزيلت في Dart الحديث، واستعمالات قديمة وتحذيرات وأمثلة حزم أجنبية خرجت من graph. هذه ليست 536 مشكلة جديدة للعميل ولا يجب إضافتها بهذا الرقم إلى التقرير التجاري. تحتاج فرزاً وإصلاحاً بحسب الأثر؛ لم يُضف تجاهل عام لها ولم تُغير البوابة exit code إلى النجاح. ملفات Paytm التي فيها تعديلات المستخدم محفوظة ولا تُمسح لتخفيض الرقم.

## فحص الأسرار والبناء

```powershell
dart tools/quality_gate.dart --security
dart tools/quality_gate.dart --build-debug
```

الأمر الأول يشغل scan ثابتاً فقط، دون Flutter أو شراء أو API حي، ويطبع مساراً وسبباً لا قيمة مفتاح. الأمر الثاني يشغل الجودة ثم scan؛ لن يبني APK ما لم ينجح كل ما سبق. لا ينتج release ولا يرفع أي ملف. رفض build-debug الآن متوقع بسبب الملاحظات القديمة والأسرار الحالية، وليس إثبات إصلاحها. يبقى حاجز Gradle الخاص ببناء release مستقلاً ولا يمكن لهذا الأمر إلغاؤه.

كل تشغيل صحيح يكتب metadata فقط في build/kanz-quality/latest.json، ويحتفظ بنسخة run-تاريخ.json للتشغيل نفسه. البيانات تتضمن وقت UTC وأسماء الفحوص وexit codes والوضع وحالة النجاح، مع deploymentApproved=false وliveIntegrationVerified=false. لا تُحفظ استجابات أو logs خام أو كلمات مرور في هذه الملفات. مجلد build مولد وقد يزول مع flutter clean؛ ملخص الدفعات المعتمد يبقى PROGRESS.md.

## إعداد GitHub Actions

الملف .github/workflows/kanz-quality.yml أضيف محلياً. يشغل quality وcredential-scan منفصلين، وبعد نجاحهما فقط يختبر بناء Android debug. يثبت Flutter إلى الإصدار الذي اختُبر محلياً، ويستخدم lockfile وصلاحية contents:read، ولا يحتفظ باعتماد Git بعد checkout ولا يستعمل secrets ولا يرفع APK أو ينشر. مراجع Actions مثبتة إلى SHA كاملة فُحصت من المستودعات الرسمية للمزودين، وليست tag قابلة للتحرك أثناء التشغيل.

لم تُدفع هذه التغييرات إلى المستودع ولم يُشغل workflow على GitHub؛ لذلك «CI فعلي أخضر» لم يتحقق. قبل دفع المشروع يلزم إزالة المواد الحساسة من النسخة المراد دفعها والتعامل مع تاريخ المستودع وتدوير المفاتيح وخطة حفظ توقيع الإنتاج. لا تُحذف ملفات المستخدم أو تُغير شهادة الإصدار المنشور عشوائياً. تشغيل CI عن بعد يتطلب مستودع GitHub وتفعيل Actions وإمكانية تنزيل الاعتماديات ومراجعة أول run، ثم سياسة required checks لدى صاحب المستودع. لا يتضمن هذا الإعداد iOS distribution أو APNs أو اختبارات دفع أو مراقبة أعطال؛ البند 14 يظل جزئياً.

مراجع الإعداد: [GitHub — اختبار Gradle](https://docs.github.com/en/actions/tutorials/build-and-test-code/java-with-gradle)، [مزود Flutter Action](https://github.com/subosito/flutter-action)، [Checkout الرسمي](https://github.com/actions/checkout). هذه المراجع تدعم إعداد workflow، لا تثبت أن مشروع كنز اجتازه.
