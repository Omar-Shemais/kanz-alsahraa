# عقد إعدادات الصفحة الرئيسية — التنفيذ والاعتماد

هذا مستند تنفيذ للبند 2، وليس إثبات نشر مصدر إعدادات على الموقع. لا يوجد اعتماد بأن تغيير HTML أو بانر الموقع يغير JSON التطبيق تلقائياً.

## ما يعمل محلياً الآن

عندما يكون appConfig رابط HTTPS لمصدر JSON عام، يبدأ التطبيق بآخر إعدادات صالحة محفوظة، أو بملف اللغة المضمن إذا كانت النسخة غير متاحة/تالفة. لا ينتظر الشبكة لعرض هذه البداية. يطلب نسخة حديثة في الخلفية عند التشغيل أو طلب التحديث؛ الطلبات المتزامنة لنفس دورة التحميل تشترك في طلب واحد.

يُحفظ JSON الكامل في SettingsBox، وليس CacheBox الذي يُنظف يومياً. التخزين يفصل الموقع ومجلد الإعدادات واللغة والمصدر ببصمة، ويحفظ schema=1 وتاريخ الحفظ وdigest للتحقق من تلف البيانات. digest ليس توقيعاً أمنياً أو حماية من مهاجم يملك الجهاز. مصدر الإعدادات يستخدم HTTPS والنقل الآمن؛ لا تُقبل استجابة غير 200 أو JSON لا يقرأه AppConfig.

نسخة قديمة سليمة تظل بديل عرض عند انقطاع الشبكة مع الاحتفاظ بتاريخها؛ ليست ضماناً لصحة سعر أو مخزون. إعادة التحقق قبل الشراء في cart_validation منفصلة. فشل القراءة لا يمسح الإعدادات، وفشل الحفظ لا يمنع استخدام نسخة الشبكة الصالحة. كتابة بدأت بالفعل قد تكتمل بعد تغيير السياق، لكنها لا تنشر تحديثاً في الواجهة؛ الكتابات مرتبة والطلبات المتأخرة لا تتجاوز دورة التحميل الأحدث.

تحديث البانرات والمحتوى يعيد نموذج الإعدادات دون إعادة إنشاء التنقل المفتوح. قائمة التبويبات الحالية تبقى حتى التشغيل التالي؛ النسخة الكاملة المحفوظة تتضمن التبويبات الجديدة كي تُقرأ عند التشغيل التالي. لا يطلق التحديث الخلفي EventLoadedAppConfig من جديد، فلا يعيد طلب نفسه ولا يقطع رحلة الدفع.

إذا كان appConfig مساراً محلياً، يحتفظ التطبيق بتحميل الملف المحلي وخطاف كاش Woo القديم عند تفعيله، مع مهلة وعدم اعتماد callback متأخر. ردود Woo التي قد تكون مخصصة للمستخدم لا تُحفظ في مستودع JSON العام. ذلك المسار لا يجعل ملفاً محلياً يتزامن تلقائياً مع بانرات الموقع.

## ما يحتاج اعتماداً وخادماً قبل إغلاق البند

1. تحديد رابط JSON عام تحت نطاق يملكه المتجر، ومصدر إدارة البانرات والأقسام، وربط حفظها بتحديث ذلك JSON. لا تُدرج مفاتيح Woo أو بيانات عميل أو أسعار خاصة بحساب في الملف العام.
2. تعيين appConfig إلى الرابط المعتمد في إعداد الإصدار. يدعم العميل ملف config_لغة.json المجاور ثم الرابط الافتراضي عند فشل ملف اللغة. يبقى query المصدر إن وجد؛ لا تستخدم رموز جلسة/اعتماد خاص في رابط عام.
3. الاستجابة المطلوبة: HTTP 200 وJSON بترميز UTF-8، وSetting كائن، وTabBar قائمة غير فارغة تحتوي layout وicon نصيين. عندما يوجد تبويب home، يلزم HorizonLayout كقائمة كائنات لكل منها layout نصي غير فارغ. عناصر المكونات الأخرى تخضع لصيغة AppConfig الفعلية؛ اجتياز الفحص الأولي وحده لا يكفي إذا كان جزء متداخل غير صالح.
4. يجب أن يمثل JSON صفحة التطبيق فعلاً، لا صفحة WordPress أو منتجاً أو رسالة خطأ. بنية الصور والأقسام تُستمد من ملفات config_ar/config_en الحالية، وتُجرَّب بصرياً على الأجهزة قبل نشرها. يُعتمد ترتيب اللغة الافتراضية والمجلدات من صاحب المتجر.
5. تحديد سياسة CDN وتحديث الكاش وإصدار المحتوى لدى الناشر، بحيث يرى العميل نسخة البانرات الحديثة. إصدار مخزن العميل schema=1 ليس إصدار محتوى خادمي، ولا يوجد ادعاء بدعم ETag أو rollback خادمي حالياً.
6. نسخة احتياطية وخطة رجوع قبل أي تعديل على الإنتاج، ثم تجربة نشر إعداد صالح وآخر تالف وشبكة بطيئة ووضع الطيران، والتحقق من حفظ السلة وعدم قطع الدفع والتبويبات على Android/iOS.

## أدلة القبول الحالية

home_config_repository_test يختبر الحفظ والعزل والتلف وفشل القراءة/الكتابة والردود المتأخرة والكتابة المرتبة، ويفتح ويغلق Hive فعلياً ليقرأ النسخة من القرص. app_home_config_test يختبر نموذج التطبيق: البداية دون انتظار رد الشبكة، مشاركة طلب التحديث، تحديث المحتوى مع إبقاء قائمة التنقل ذاتها، قراءة التبويبات الجديدة عند إعادة إنشاء النموذج، وفشل الشبكة واستبدال الإعدادات والتخلص من النموذج أثناء طلب معلق.

هذه اختبارات محلية بمصادر مصطنعة، ولا تثبت أن بانرات الموقع الحي متصلة بالمصدر أو أن الشاشات ظهرت سليمة على الأجهزة. البند يظل جزئياً حتى نشر واعتماد ذلك التكامل.
